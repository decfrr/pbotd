# pbotd 日本語利用ガイド

[English README](README.md)

**pbotd（PBS On The Desktop）** は、1 台の Linux マシン上で、自分のジョブを CPU・メモリ・GPU の空きに応じて順番に実行するツールです。PBS 形式の `.pbs` ファイルを投入でき、GPU の割り当て、ジョブ配列、依存関係、実行時間制限などを利用できます。PBS Professional の一部の操作に対応しており、PBS サーバーの設置は不要です。

**必要な実行環境がそろっていれば、インストールも通常の利用も一般ユーザー権限で完結します。`sudo` は不要です。** 最初は `--no-aliases` でインストールし、`pbotd qsub` のように使う方法を推奨します。既存の PBS コマンドと区別しやすくなります。

## 1. 必要な環境

| 項目 | 必要なもの |
| --- | --- |
| OS | Linux。Windows では WSL2 内の Linux を利用してください。Windows ネイティブ・macOS 上でのジョブ実行には対応していません。 |
| ビルド環境 | **Go 1.27 以上**。インストーラーがソースからビルドします。ビルド済みの、OS・CPU に合う実行ファイルを使う場合、実行先に Go は不要です。 |
| シェル | 標準設定では `/bin/bash`。インストーラーには `/bin/sh` と `mkdir`、`mktemp`、`readlink` などの標準的な Linux コマンドを使います。 |
| ソースの取得 | 以下の手順では Git を使います。ソース一式を別の方法で入手済みなら Git は不要です。 |
| ネットワーク | ソース取得時と、未取得の Go 依存パッケージをビルド時にダウンロードする際に必要です。通常のジョブ管理はローカルで動作します。 |
| CPU・メモリ | ジョブの要求量が設定上の利用可能量に収まること。既定のメモリ設定については下記を参照してください。 |
| 保存先 | 実行ファイル・設定・状態保存先に書き込めること。状態を保存する SQLite データベースは **ローカルディスク** に置いてください。 |
| 実行するプログラム | Python、学習用ライブラリ、実行データなど、そのジョブ自体が必要とする環境。pbotd はこれらをインストールしません。 |

CPU ジョブには GPU は不要です。pbotd 本体のビルド・実行に C コンパイラ、外部の SQLite サーバー、PBS Professional、Docker、systemd は必要ありません。`make` もインストーラーを直接実行する場合は不要です。

Go がない場合は、管理者が用意した Go、または[公式配布物](https://go.dev/doc/install)をユーザーが書き込める場所に展開した Go を利用できます。その `go/bin` を `PATH` に追加してください。Go コマンドの設定によっては、ビルドに必要なツールチェーンを自動ダウンロードします。詳しくは [Go Toolchains](https://go.dev/doc/toolchain) を参照してください。

### GPU ジョブを使う場合の追加条件

- NVIDIA GPU と対応ドライバーがあり、**利用する一般ユーザーで GPU を操作できること**。
- 標準設定では、そのユーザーで `nvidia-smi` による GPU 情報と実行中の GPU プロセス情報を取得できること。
- CUDA アプリケーションを実行する場合は、そのアプリケーションが必要とする CUDA ランタイムなどがあること。CUDA Toolkit の導入は pbotd 本体の必須条件ではありません。

pbotd のインストーラーは GPU ドライバーの導入やデバイス権限の変更を行いません。WSL の GPU 利用には Windows 側の対応環境も必要です。[NVIDIA の WSL ガイド](https://docs.nvidia.com/cuda/wsl-user-guide/index.html)を確認してください。

### 既定のメモリ設定

初期設定では、検出したメモリ上限からホスト用の **2 GiB** を差し引き、ジョブ 1 件の既定要求を **1 GiB** とします。このため、設定を変更せずに起動するには、検出した上限が少なくとも 3 GiB 必要です。コンテナーなどではホスト全体より低い上限が使われる場合があります。

これは pbotd 自身が 3 GiB のメモリを消費するという意味ではなく、ジョブを受け付けるための予算です。小さなマシンでは、初回起動前に第 4 節の設定を調整してください。

## 2. インストール方法

以下は、Linux または WSL2 内の端末で、利用する一般ユーザーとして実行します。

```sh
go version  # Go 1.27 以上を確認

git clone https://github.com/decfrr/pbotd.git
cd pbotd
./scripts/install.sh --no-aliases

export PATH="$HOME/.local/bin:$PATH"
pbotd --version
```

これで `~/.local/bin/pbotd` が使えるようになります。ソースを入手済みの場合は、そのディレクトリで `./scripts/install.sh --no-aliases` から実行してください。

`export PATH=...` は現在の端末に対する設定です。次回以降も使うには、自分のシェルの設定ファイルに同じ行を追加してください。インストーラーは `.bashrc` や `.profile` を編集しません。`PATH` を変更せず、`~/.local/bin/pbotd` と絶対パスで呼び出すこともできます。

### `qsub`、`qstat` などの名前で使いたい場合

`--no-aliases` を付けずにインストールすると、次の名前のシンボリックリンクも作成します。

```sh
./scripts/install.sh
```

```text
qsub qstat qdel qhold qrls qalter qrerun pbsnodes
```

リンク先は同じディレクトリの `pbotd` です。たとえば `qsub job.pbs` と `pbotd qsub job.pbs` は同じ操作になります。

**衝突チェックの対象はインストール先のディレクトリだけです。** そこに既存の PBS コマンドや別のリンクがあると、インストーラーはビルド・置換前にエラーで終了します。ただし `/usr/bin/qsub` など別の場所にあるコマンドは検査しません。`~/.local/bin` を `PATH` の先頭にすると、そちらより pbotd のリンクが優先されます。既存の PBS も使う環境では、`--no-aliases` を推奨します。

### インストール先を指定する場合

```sh
./scripts/install.sh --bin-dir "$HOME/tools/pbotd/bin" --no-aliases
"$HOME/tools/pbotd/bin/pbotd" --version
```

自分が書き込めるディレクトリを選んでください。`--bin-dir` が変更するのは実行ファイルとリンクの保存先だけで、設定・ジョブ履歴の保存先は変わりません。

## 3. インストール中に何が起きるか

[インストーラー](scripts/install.sh)が行う処理は次のとおりです。

1. Linux であることを確認し、リンクを作成する場合は保存先の衝突を確認します。
2. インストール先と、その中の一時ディレクトリを作成します。
3. `CGO_ENABLED=0 go build -trimpath` で pbotd をビルドします。必要に応じて Go が依存パッケージなどをダウンロードし、Go のキャッシュに保存します。
4. ビルドした実行ファイルをモード `0755` で `pbotd` として配置します。**同名の既存 `pbotd` は確認なしで置き換えます。** ビルドに失敗した場合は、この置き換えには進みません。
5. 指定に応じて PBS コマンドのリンクを作成し、一時ディレクトリを削除します。既存の `pbotd` 向けリンクはそのまま利用します。

| 対象 | インストール時の扱い |
| --- | --- |
| `~/.local/bin/pbotd` | 作成、または更新します。`--bin-dir` で変更できます。 |
| `qsub` などのリンク | `--no-aliases` なら作成しません。このオプションで既存リンクが削除されることもありません。 |
| Go のキャッシュ | ビルドにより作成・更新されることがあります。保存先は `go env GOMODCACHE GOCACHE` で確認できます。 |
| 設定ファイル・ジョブデータ | インストーラーは作成・変更しません。設定ファイルは任意、ジョブデータは利用開始時に作成します。 |
| 常駐プロセス・自動起動サービス | インストールしただけでは起動・登録しません。 |
| シェル設定・システム設定 | `PATH`、シェル設定、`/etc` の設定、GPU ドライバー、ユーザー権限を変更しません。 |

初回の `pbotd qsub` や `pbotd qstat` では、標準設定なら自分の権限でデーモンが自動起動し、状態保存用ディレクトリなどが作成されます。**インストールとデーモンの初回起動は別の処理です。** `pbotd --version`、`pbotd status`、`pbotd doctor` はデーモンを自動起動しません。

## 4. 一般ユーザーで使うための設定と保存先

通常は設定ファイルなしで使えます。設定する場合、既定の場所は `~/.config/pbotd/config.toml` です。全項目の例は [examples/config.toml](examples/config.toml) にあります。設定はデーモン起動時に読み込むため、変更を反映するにはデーモンの再起動が必要です。

たとえば、メモリ上限が小さいマシンでは、初回起動前に次のような設定を保存できます。省略した項目には既定値が使われます。

```toml
[resources]
memory_reserve = "512MiB"

[defaults]
mem = "128MiB"
```

この例では、検出した上限から 512 MiB を引いた範囲をジョブ用とし、要求を省略したジョブに 128 MiB を割り当てます。実際のジョブに必要なメモリは `-l mem=...` で指定してください。

### ファイルの保存先

| 内容 | 既定の保存先 |
| --- | --- |
| 実行ファイル | `~/.local/bin/pbotd` |
| 任意の設定ファイル | `~/.config/pbotd/config.toml` |
| 履歴・状態データベース | `~/.local/state/pbotd/<ホスト名>/pbotd.db` |
| 投入スクリプトのコピー・実行結果 | 上記ホスト別ディレクトリの `jobs/` 以下 |
| 自動起動したデーモンのログ | 上記ホスト別ディレクトリの `daemon.log` |
| ローカル通信用ソケット | `$XDG_RUNTIME_DIR/pbotd/pbotd.sock`。未設定なら上記ホスト別ディレクトリの `run/pbotd.sock` |
| ジョブの標準出力・標準エラー | 投入時の作業ディレクトリ。`-o`、`-e` で変更できます。 |

`XDG_CONFIG_HOME` または `XDG_STATE_HOME` が設定されていれば、それぞれ `~/.config`、`~/.local/state` の代わりに使います。`PBOTD_CONFIG`、`PBOTD_STATE_DIR`、`PBOTD_SOCKET` では各保存先を直接指定できます。

ホームディレクトリが NFS などの共有ストレージにある場合は、`PBOTD_STATE_DIR` をローカルディスク上の自分専用ディレクトリに変更してください。ソケットの保存先にも自分専用のディレクトリを使ってください。状態ディレクトリは `0700`、内部ファイルとソケットは `0600` で管理され、他の UID からの操作は受け付けません。

### root 権限が必要になる境界

| やりたいこと | 一般ユーザーでの利用条件 |
| --- | --- |
| CPU ジョブの投入・実行・停止 | 自分のファイルを読み書きでき、プログラムを実行できれば利用できます。標準機能に特権設定は不要です。 |
| GPU ジョブの実行 | そのユーザーが既に GPU を利用できる必要があります。ドライバー導入やデバイス権限の整備は、環境によって管理者の作業になります。 |
| CPU・メモリ使用量の強制制限 | 既定ではジョブの受付量を管理する予約です。強制制限には任意機能の cgroup v2 と、利用者への委譲が必要です。委譲されていない環境では管理者の設定が必要になる場合があります。 |
| ログアウト後も実行を続ける | ホストのログアウト時のプロセス終了方針に依存します。systemd のユーザーサービスや lingering の設定が必要になる場合があります。 |

pbotd は **1 ホスト・1 ユーザー用** です。別ユーザーの pbotd と GPU 予約を共有する仕組みはありません。既定では他の GPU プロセスを検出して待機しますが、別プロセスの GPU 利用そのものを禁止する機能ではありません。共有計算機では、管理者の利用方針や既存スケジューラーの割り当てに従って使ってください。

これまでに Linux ARM64 の隔離環境で、一般ユーザー（UID 65534、UID 1000）による実行と systemd ユーザーサービスを検証しています。実機の NVIDIA GPU と WSL での動作は未検証です。環境ごとの確認方法は [テスト手順（英語）](docs/testing.md)に記載しています。

## 5. 最初のジョブを動かす

ソースのディレクトリで次を実行します。CPU の例なので GPU は不要です。

```sh
pbotd qsub examples/cpu.pbs
# 例: 1.localhost というジョブ ID が表示される

pbotd qstat -x
pbotd status
pbotd doctor
```

`qstat -x` では完了済みジョブも表示します。詳細は、実際に表示された ID を使って確認してください。

```sh
pbotd qstat -f 1.localhost
```

正常終了すると詳細表示の `state` が `COMPLETED`、`Exit_status` が `0` になります。この例では出力は `hello.o1` に保存されます（末尾の番号は実際のジョブ番号です）。別の作業ディレクトリから投入すると、出力もその作業ディレクトリに保存されます。

GPU の動作を確認する場合は、まず同じユーザーで次のコマンドを実行してください。

```sh
nvidia-smi
pbotd pbsnodes -a
pbotd qsub examples/gpu.pbs
```

既定の GPU 方針は、外部プロセスによる使用を避ける `avoid` です。プロセス情報を取得できない場合は GPU ジョブを待機させます。CPU ジョブは利用できます。原因は `pbotd doctor --json` と `pbotd pbsnodes -a --json` で確認してください。`ignore` は外部利用の確認を省略する設定なので、動かない場合の一律の対処として変更することは推奨しません。

## 6. 起動方法とよくある問題

通常はクライアントからの自動起動で利用できます。端末上でデーモンを管理したい場合は、別のデーモンが動作していない状態で次を実行します。

```sh
pbotd daemon --foreground
```

Ctrl-C でデーモンを停止できます。ただし **デーモンの停止はジョブのキャンセルではありません**。実行中のジョブは独立した監視プロセスの下で継続します。ジョブを止める場合は、デーモンの稼働中に `pbotd qdel JOB_ID` を使ってください。ホストの再起動をまたいで実行が継続するわけではありません。

systemd は任意です。[同梱のユーザーサービス](contrib/systemd/pbotd.service)を使う場合は、[運用手順（英語）](docs/operations.md)の手動設定を行ってください。インストーラーによるサービス登録はありません。

| 症状 | 確認・対処 |
| --- | --- |
| `pbotd: command not found` | `PATH` を確認するか、`~/.local/bin/pbotd` を直接実行します。 |
| Go のバージョンやダウンロードで失敗する | `go version`、ネットワーク接続、Go キャッシュへの書き込み権限を確認します。 |
| `Refusing to replace ...` | インストール先のコマンド名が衝突しています。`--no-aliases` または別の `--bin-dir` を選びます。 |
| `default job does not fit configured capacity` | 第 4 節のメモリ設定、CPU 数、コンテナーの資源上限を確認します。 |
| インストール直後の `status`／`doctor` が接続エラーになる | これらのコマンドは自動起動しません。`pbotd qstat` または `pbotd daemon --foreground` で起動します。 |
| 状態ディレクトリなどで権限エラーになる | 自分が所有する保存先を選びます。`sudo` で再実行せず、以前の実行ユーザーや環境変数による保存先変更を確認します。 |
| GPU ジョブが待機し続ける | GPU の割り当て状況、外部プロセス、`nvidia-smi` の取得結果を `doctor` と `pbsnodes` で確認します。 |
